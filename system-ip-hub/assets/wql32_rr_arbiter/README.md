# Round-Robin 轮询仲裁器

## 当前结论

该实现的基础轮询逻辑可用，但必须保证 `i_grant_en` 只在一次 grant 被真正接受时拉高，并保持请求语义稳定。`REQ_NUM=1` 存在索引位宽问题，建议限制为 `REQ_NUM >= 2` 或增加专门分支。

## 功能概述

模块对 `REQ_NUM` 路请求执行 round-robin 仲裁。它记录上一次被接受的 grant，并优先搜索其后的请求；若高索引区域没有请求，则回绕到低索引区域。

输出包括：

- `o_grant`：one-hot grant。
- `o_grant_id`：被选请求的二进制索引。
- `o_grant_vld`：当前至少存在一个可授予请求。

## 仲裁状态更新

组合逻辑会根据当前请求和 `last_grant` 立即生成候选 grant。只有在以下条件同时满足时，轮询指针才应前进：

```text
i_grant_en && o_grant_vld
```

因此，`i_grant_en` 不能简单表示“仲裁器使能”，而应表示“当前 grant 已被下游接受”。若下游反压，应保持 `i_grant_en=0`。

## 公平性与优先顺序

- 对持续保持的多个请求，只要每次 grant 最终都会被接受，各请求可获得无饥饿轮询服务。
- 优先编码器在候选集合内选择最低索引请求。
- 复位后 `last_grant` 的初值会影响第一次仲裁的起始位置；当前实现相当于从其后一个索引开始搜索，再回绕。

## 使用限制与注意事项

- `REQ_NUM=1` 时 `$clog2(REQ_NUM)` 为 0，当前 `o_grant_id` 端口会形成非法或工具相关的零宽度声明。
- grant 是组合输出，模块不会在反压期间自动锁存选择结果。调用者应保持 request，且不要误拉高 `i_grant_en`。
- 如果请求会在未被接受前撤销，grant 可能随组合输入变化；需要稳定 grant 时应增加锁存状态或使用 ready/valid 接口。
- 模块不检查 `o_grant` 的 one-hot 合法性，建议添加断言。

## 建议验证项

1. 单请求和所有请求同时持续拉高。
2. 随机请求配合随机 `i_grant_en`，使用参考模型比较轮询顺序。
3. grant 未接受时保持/撤销请求，确认接口约定符合系统需求。
4. 检查长时间运行下无饥饿、grant one-hot0、grant id 与 one-hot 一致。
5. 测试 `REQ_NUM=2`、非 2 的幂和较大端口数。
6. 增加断言：`$onehot0(o_grant)`，以及 `o_grant_vld == |o_grant`。
