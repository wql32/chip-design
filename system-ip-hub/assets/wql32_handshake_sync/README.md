# 4 相握手同步器

## 当前结论

该模块采用多周期路径加四相握手的 CDC 思路，但目的端请求沿检测逻辑方向错误，正常情况下无法产生有效的 `dst_vld` 脉冲。当前版本不能直接用于跨时钟域传输。

## 设计意图

模块希望把一组多 bit 数据从源时钟域可靠传到目的时钟域：

1. 源域锁存输入数据并拉高 `req`。
2. `req` 经过两级同步器进入目的域。
3. 目的域检测到请求后采样保持稳定的数据总线，并拉高 `ack`。
4. `ack` 经过两级同步器返回源域。
5. 源域看到 `ack` 后撤销 `req`，目的域随后撤销 `ack`，完成四相握手。

数据总线本身不逐 bit 同步，而是在握手期间保持不变，属于 multi-cycle path（MCP）CDC 结构。

## 接口行为

- 源端只有在同步器空闲时才能接收新数据。
- 目的端没有 ready 输入；成功接收时预期产生一个周期的 `dst_vld` 脉冲。
- 一次传输必须等待完整的 req/ack 往返，吞吐率明显低于异步 FIFO。
- 适用于低带宽控制信息或配置数据，不适合连续高速数据流。

## 已知问题

- 当前请求脉冲逻辑类似 `req_sync_1 && !req_sync_0`。其中 `req_sync_0` 是较新的同步级、`req_sync_1` 是较旧的同步级，该表达式检测的是不成立的时序组合，无法正确检测上升沿。
- 正确实现需要在目的域对“已经完成两级同步的 req”再保存一个延迟版本，并比较 `req_sync && !req_sync_d`。
- 多 bit 数据总线需要在源域从发起请求到握手完成期间保持稳定，并配置对应 CDC/MCP 约束。
- 两个时钟域的复位释放需要各自同步，避免状态机停留在 req/ack 不一致状态。
- 目的端没有反压能力；若消费者不能无条件接收单周期 `dst_vld`，还需要增加 ready 或目的端缓存。

## 修复建议

1. 重写目的域边沿检测，并对同步后的请求增加独立延迟寄存器。
2. 明确源端 `src_ready` 或 busy 语义，禁止握手未完成时覆盖数据寄存器。
3. 若目的端可能反压，改为 ready/valid 握手或在目的域增加 skid buffer。
4. 为 req、ack 标注异步同步寄存器属性，并建立 CDC/MCP 约束。
5. 对独立复位或单边复位场景定义恢复策略。

## 建议验证项

- 两个时钟使用不同频率、不同相位和动态频率比。
- 在握手的每个阶段施加复位。
- 连续发起请求，确认 busy 期间不会覆盖数据。
- 每次源端接受的数据必须在目的端出现且只出现一次。
- CDC 工具检查同步链与多周期数据稳定性。
